## Scope and activation

This implementation is prepared for integration, **not certified against real
RabbitMQ/PostgreSQL**. Shared contracts, dashboard services and Docker Compose
were not changed. There is no email, SMS, external delivery provider, STOMP alert
publisher, user-specific inbox or read receipt.

Defaults are deliberately inactive:

- `NOTIFICATION_STORAGE_ENABLED=false`: no DataSource is created; REST returns 503.
- `NOTIFICATION_MESSAGING_ENABLED=false`: no notification listener/admin/topology
  is instantiated. Rabbit automatic declaration and health checks are disabled.
- `spring.flyway.enabled=false`, `spring.sql.init.mode=never`: no migrations or
  alternative table initialization. V1 is a review artifact only.
- HTTP binds to loopback on proposed port 8082. DEV 3 must approve deployment
  port/network configuration; Compose does not currently include this service.

`.env.example` documents public names and empty secret placeholders. Spring does
not load it automatically. Supply authorized environment configuration through
the team's private mechanism. Never commit passwords or use dashboard's queue.
No database, match ID or password is generated by this service.

Before any future activation the team must separately authorize schema migration,
infrastructure, credentials, match bindings and delivery. Apply V1 **through
Flyway only**, with a dedicated history table/default schema `notification`.
The application then needs runtime DML/SELECT permissions, not schema creation
rights. Storage startup checks existing tables without issuing DDL. Migration
execution and actual consumer activation were not performed in Fase 3B.1.

## Architecture and files

```text
RabbitMQ live_updates
  -> ScoreUpdateListener / ScoreUpdateCodec
  -> ProcessScoreUpdateService / NotificationPolicy
  -> NotificationStore
  -> JdbcNotificationStore: inbox + optional alert in one transaction

GET /api/alerts -> AlertController -> NotificationStore.query
```

- `domain/`: immutable ScoreUpdate, LiveAlert and approved event policy.
- `application/`: repository port and process use case.
- `infrastructure/json/`: isolated Jackson 2 inbound mapper using Boot-managed
  versions. Boot 4 retains its managed Jackson 3 mapper for MVC; no global mapper
  replacement or runtime dependency on dashboard classes.
- `infrastructure/jdbc/`: PostgreSQL adapter and scoped cursor.
- `infrastructure/amqp/`: manual acknowledgements, bounded retry and confirmed DLQ.
- `infrastructure/config/`: explicit storage/messaging opt-ins and exact CORS origins.
- `infrastructure/web/`: local REST DTO and sanitized errors.
- `db/migration/V1__notification_inbox_and_alerts.sql`: prepared, not executed.

## Existing inbound contract

Source: `match-state-service` publication code, not the currently empty shared
schema. JSON snake_case with `match_id`, `event_id`, `event_type`, `home_score`,
`away_score`, `var_status`, `updated_at`, nullable/optional `reference_event_id`.
Integers must fit Java int and be non-negative; timestamps use Instant with
nanosecond precision. Annulment requires a non-blank reference. Unknown fields,
duplicate JSON properties, trailing documents, coercion and bodies over 64 KiB
are rejected. Wire validation deliberately follows the existing consumer's strict
compatibility; a future ScoreUpdate field requires coordination with DEV 1.

When AMQP message_id/routing metadata is present, it must agree with the body.
No team, player, minute, recipient or source epoch is invented. Source time is
Match State processing time, not the sporting event's original timestamp.

| Event | Result |
|---|---|
| GOAL | Visible alert with supplied score |
| VAR_CHECK | Visible review alert |
| GOAL_ANNULLED | Visible annulment alert, preserving source reference |
| MATCH_CONTINUES | Durable inbox entry marked SUPPRESSED; no visible alert |

## Atomicity and duplicates

Inbox uniqueness is `(source, match_id, event_id)`, with logical source fixed to
`match-state-service`. INSERT ON CONFLICT resolves competing receipts. Existing
normalized payloads are compared as validated domain values: JSON field order,
equivalent Instant representations and missing/null optional reference do not
create a conflict. A real content change under the same identity is quarantined
through DLQ; original inbox/alert records are never overwritten.

Inbox insertion, cursor allocation and alert insertion share a REQUIRES_NEW JDBC
transaction, so the repository returns only after its own commit, even if a
caller has another transaction. Failure rolls back the whole operation. Listener
ACK occurs afterwards. A lost ACK may cause redelivery; deduplication prevents a
second visible alert and preserves the first alert UUID/content/creation time.

MATCH_CONTINUES is also deduplicated. Changing policy later does not automatically
reprocess prior suppressed entries. There is no purge/retention job or automatic
replay in this phase.

**Unresolved source restoration identity:** ScoreUpdate contains no source epoch.
Reusing `(match_id,event_id)` after restoring/replacing the producer may be treated
as a duplicate or conflict. The notification cursor epoch does not solve source
identity. DEV 1/DEV 3 must agree on identity and restore/replay procedures before
integration. Do not silently change source namespace to bypass deduplication.

## Proposed RabbitMQ topology, not provisioned

- Existing source exchange: `live_updates`, durable topic.
- Owned queue: `notification.score-updates`, durable, configurable with mandatory
  `notification.` prefix; `mvp-dashboard-scores` is rejected.
- Binding per authorized `NOTIFICATION_MATCH_IDS`: `score.{matchId}`. No wildcard
  subscriptions; no generated match default.
- The complete routing key, including `score.`, must fit 255 UTF-8 bytes. The
  existing ASCII explicit-ID allowlist remains unchanged; multibyte byte-budget
  tests exercise the independent length validator without widening that policy.
- Owned direct DLX: `<queue>.dlx`, durable; DLQ: `<queue>.dlq`, durable; key `rejected`.
- One consumer, prefetch 1, MANUAL ACK; no competing dashboard consumer.
- Correlated confirms, publisher returns and mandatory publication are required.

Three attempts total by default, waiting 1s and 2s between transient failures.
`ProcessingFailurePolicy` distinguishes permanent input/identity and non-transient
JDBC errors (integrity, syntax, permission), transient connection/lock/transaction
failures, and unknown failures. Resource availability failures remain retryable
even when Spring wraps them as non-transient. Wrapped causes are inspected with
cycle/depth protection; a known permanent cause takes precedence. Unknown runtime
failures receive bounded retries before confirmed DLQ transfer.
Configuration is bounded to 1..10 attempts, 1..10000ms base delay, maximum 30s
per delay. Validation/identity failures skip retries. After failure, a persistent
copy of the original body is transferred to DLQ, preserving original routing
metadata and recording only failure type (no raw exception text). Expiration is
removed from the DLQ copy. Only a routed, positive confirm permits ACK of input.

NACK/return/timeout/send failure during DLQ transfer results in requeue of the
original and stopping this consumer. An interrupted backoff also retains input.
If the channel fails before ACK/NACK, the broker's unacknowledged-delivery recovery
must be verified in real integration. There is no automatic DLQ replay. Correct
the cause and explicitly resume/replay under the agreed operational procedure.

The queue must be provisioned/bound before source events are published. A durable
queue preserves deliveries only after routing to it; past events are not replayed
simply by starting this service. Publisher confirms alone cannot prove routing to
every intended independent consumer queue.

## REST, cursor and local LiveAlert DTO

```text
GET /api/alerts?match_id=<authorized-id>&limit=50
GET /api/alerts?match_id=<authorized-id>&after=<opaque-cursor>&limit=50
```

`match_id` is mandatory; limit is 1..100. Response:

```json
{ "items": [], "next_cursor": "opaque-checkpoint", "has_more": false }
```

Each item is a **service-local proposed DTO**, not an approved shared schema:
`contract_version` (1.0), `alert_id`, `match_id`, `alert_type`, `source_event_id`,
`source_updated_at`, `created_at`, `reference_event_id`, `home_score`, `away_score`,
`var_status`, `content` (`locale`, `title`, `message`). Shared LiveAlert publication
and changes to `contracts/events/live-alert.schema.json` remain blocked.

The initial page returns the latest window, ordered oldest to newest within that
window, and a checkpoint for subsequent polling. It intentionally does not expose
older-history pagination. Incremental pages return alerts after the checkpoint
in ascending committed local sequence. If has_more=true, drain additional pages
before waiting for the next poll. Empty responses still supply a checkpoint.

The sequence allocator is one PostgreSQL row updated inside the writer transaction;
its lock serializes allocation through commit. A raw BIGSERIAL could let a polling
cursor skip a delayed earlier commit. Reads capture an upper committed sequence
and bound results by it. This is local processing order, not sporting event order.

The base64url cursor includes version, persistent notification epoch, match scope
and exact 64-bit sequence encoded as text. It is opaque and validated, but is not
an authentication credential. Malformed/wrong-match cursors return 400. An epoch
mismatch or a checkpoint ahead of a restored DB returns 409; reload the initial
window. DB restore with an unchanged epoch and compatible sequence is not always
detectable: coordinated epoch rotation/restore procedures remain pending.

Responses disable caching. Disabled/unavailable storage returns 503; internal
details/passwords are not returned. Default CORS grants no cross-origin access;
`NOTIFICATION_ALLOWED_ORIGINS` accepts only exact HTTP(S) origins for GET. No user
authentication is added; current scope is internal/local and not a public service.
Frontend integration is not part of 3B.1.

## Local verification (no infrastructure)

### Functional readiness (Fase 3B.3)

`GET /actuator/health/liveness` reports process liveness independently of external
dependencies. `GET /actuator/health/readiness` requires startup completion, enabled
storage, a valid PostgreSQL connection, enabled messaging and an operational owned
consumer. Its boolean details expose `service_started`, `storage_enabled`,
`postgres_available`, `consumer_enabled`, `consumer_registered`,
`consumer_operational` and `ready`, without endpoints, credentials or exception text.
The current durable-consumer service mode requires both storage and consumer;
there is no profile that silently makes either dependency optional.

Disabled dependencies/startup pending yield OUT_OF_SERVICE; unavailable enabled
dependencies yield DOWN; only all required conditions yield UP (ready=true).
Consequently the inactive default configuration is deliberately not READY. Health
readiness uses the normal Actuator non-UP HTTP status mapping (503).

Consumer readiness requires the owned queue's ConsumeOk event, a running/active
container and a positive active-consumer count. Consumer failure/stop/restart,
connection closure/shutdown and explicit DLQ custody stop invalidate that state;
fresh acceptance is required after recovery. Publisher-only connections are
excluded from the input-consumer connection listener. These are observations of
the client's current state, not proof of future delivery or DLQ routing health.

When storage is explicitly enabled, an actual readiness request obtains a pooled
connection and calls JDBC isValid(2); normal Hikari acquisition timeout also
applies. Default-disabled health and all local readiness tests use no external
connections. Process liveness stays independent to avoid DB outages triggering
unnecessary process restarts.

Confirm timeouts below 1 ms are rejected, including positive submillisecond values.
Fractional values at or above 1 ms round upward; overflow is rejected. No positive
timeout silently becomes zero or is shortened by truncation.
